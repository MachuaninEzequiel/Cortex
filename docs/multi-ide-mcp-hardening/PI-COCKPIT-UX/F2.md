# F2 — Cortex Autopilot (gates + hotkeys virtuales + sugerencias)

Segunda fase del overhaul UX. Agrega la **capa de guidance** sobre la
base que sembró F1: hotkeys cortos prefijados con `:`, sugerencias
contextuales que el cockpit renderiza, y gates de gobernanza que
detectan violaciones de contrato Cortex con feedback temprano.

> Estado: ✅ **completa**

## Lo que entrega

### 1. `cortex-autopilot.ts` (nueva extension)

Tres responsabilidades independientes en una misma extensión:

#### A. Hotkeys virtuales (interceptor `pi.on("input", ...)`)

El usuario tipea un atajo corto prefijado con `:` en el prompt; el
handler lo intercepta **antes** de que llegue al agent y lo traduce a
un slash command o a una notificación. Cero costo de tokens.

| Atajo | Acción |
|---|---|
| `:n` | Anuncia la sugerencia activa con su `reason` |
| `:t` | Placeholder hasta F5: instrucciones manuales `just role-*` |
| `:d` | Hint para cambiar a documenter |
| `:r` | Transforma a `/cortex-role` (slash command de cortex-net) |
| `:m` | Transforma a `/cortex-mode` (slash command de cortex-net) |
| `:l` | Transforma a `/cortex-net` (slash command de cortex-net) |
| `:?` | Lista todos los hotkeys |

**Mecánica:** el handler retorna uno de:
- `{ action: "transform", transformed: "/comando" }` — reescribe input.
- `{ action: "handled" }` + `ctx.ui.notify(...)` — muestra mensaje y bloquea el envío al agent.
- `{ action: "continue" }` — pasa al agent normal.

**Por qué prefijo `:`** (decisión del usuario): evita chocar con texto
natural. Si tipeás `t` solo, va al agent normal. Si tipeás `:t`, lo
captura el autopilot. Cualquier `:xx` no mapeado se deja pasar al agent
por si es contenido legítimo (p.ej. tiempo `12:30`).

#### B. Gates de gobernanza (interceptor `pi.on("tool_call", ...)`)

Detecta violaciones de contrato Cortex y emite warning ANTES del
round-trip al backend MCP. **No bloquea** — el backend ya tiene sus
propios gates más estrictos; esto es UX defensiva.

Gate implementado en F2:
- **`cortex_create_spec` sin `cortex_sync_ticket` previo**: warning con
  explicación. El backend rechaza igual; el warning evita la confusión
  de ver el error de gobernanza sin contexto.

**Estado local**: un `Set<string>` de tools llamadas en este proceso.
Limpio en `session_shutdown`. No es perfecto en multi-terminal (otra Pi
puede haber llamado sync_ticket), pero el flujo canónico es que sync
corre en UN solo proceso antes de que workers entren a la red, así que
el set cubre el caso real. Si false-positiva, no rompe nada (es solo
notify).

Gates futuros (no en F2): `cortex_close_session` con `status="closed"`
cuando hay `unimplemented` (requiere leer SessionStorage o briefing
MCP); cierre sin documenter (requiere hook adicional).

#### C. Sugerencias contextuales (escribe `cortexState.suggestion`)

Tras cada `before_agent_start` y `turn_end`, recalcula la próxima
acción sugerida según el estado y la escribe al singleton. El cockpit
la renderiza con su hotkey si la tiene.

**Reglas en orden de prioridad** (primera que matchea gana):

| Condición | Sugerencia | Hotkey |
|---|---|---|
| `sessionId === null` | "Tipeá tu tarea — cortex-sync va a abrir la sesión" | `null` |
| `activeAgentName === "cortex-sync"` | "Esperando que cortex-sync persista la spec" | `null` |
| `myRole === null` (middle, no sync) | "Cambiá a un agent del medio (/system → cortex-SDDwork)" | `null` |
| `myRole === "documenter"` | "Llamá cortex_documenter_briefing + cortex_close_session" | `null` |
| `myRole !== null, peers.length === 0` | "Sin peers — abrí terminales con `just role-*`" | `:t` |
| `myRole !== null, peers.length > 0` | "Coordiná con peers" | `:l` |

La función es pura sobre `cortexState`, así que es trivial de extender
con nuevas reglas. F3 va a agregar reglas para `peer.status` (idle/busy)
y F5 puede agregar reglas para team-related actions.

### 2. `settings.json`

`cortex-autopilot.ts` agregado a `defaultExtensions` después de
`cortex-cockpit.ts`. El orden importa: el autopilot escribe la
`suggestion` que el cockpit lee, pero como la comunicación es vía
singleton + suscripción, cualquier orden funcionaría — convención.

## Decisiones tomadas

| Decisión | Elección | Justificación |
|---|---|---|
| Prefijo de hotkeys | `:` (dos puntos) | Decisión explícita del usuario en el debate previo. Evita chocar con texto natural. |
| Bloquear vs warning en gates | **Warning, no bloqueo** | El backend MCP ya bloquea con validación robusta. Duplicar la lógica de bloqueo en UI agrega bugs sin sumar enforcement real. La UI mejor advierte temprano. |
| Estado de tools llamadas | Set local por proceso | Multi-terminal trade-off conocido y aceptable. Sync corre en UN proceso. |
| Notify de bienvenida | Sí, en `session_start` | Descubrimiento: el usuario sabe que existe el `:?` desde la primera sesión. |
| Recalcular sugerencia | En `before_agent_start` + `turn_end` | Cubre los dos momentos donde el contexto cambia significativamente. |

## Contratos con otras fases

### Lee del singleton
- `sessionId`, `activeAgentName`, `myRole`, `peers` — todo lo que la
  función `computeSuggestion` necesita.

### Escribe al singleton
- `suggestion` (todos los `pi.on` que recalculan).

### Interactúa con cortex-net.ts
- Los hotkeys `:r`, `:m`, `:l` delegan a slash commands ya definidos en
  cortex-net.ts. Si se renombran allá, hay que actualizar el mapping
  acá.

### Espera de F4 (panel)
- `:t` hoy emite warning hardcoded. Cuando F5 (`cortex-team`) exista,
  cambiar `:t` a `{ kind: "slash", command: "/cortex-team" }` (1 línea).
- `:d` hoy emite hint hardcoded. Cuando F4 (panel) tenga "Cambiar a
  documenter" como acción navegable, podríamos cambiar `:d` a una
  transformación que abra el panel en esa acción.

## Gaps abiertos (no bloqueantes)

1. **`pi.on("input")` no está 100% documentado** en cuanto al shape de
   `event`. Asumo `event.text` (basado en docs externas y el patrón
   `input` mencionado en extensions.md). Si en runtime resulta ser
   `event.input` o `event.data`, hay que ajustar la lectura. La defensa
   con `(event as any).text ?? ""` evita crash.
2. **`pi.on("tool_call")`**: idem. Asumo `event.tool.name` o `event.name`.
   La doble defensa cubre ambos shapes.
3. **Auto-detección de "todos los checkpoints emitidos"** para sugerir
   documenter: requiere leer `cortex_session_status` o el JSON del
   SessionStorage. Postergado hasta F3 cuando el polling de peers con
   status push haga más fácil saber qué pasó.

## Cómo probarlo (manual)

1. Setup adopter + `just cortex`.
2. Esperar notify de cockpit + notify de autopilot.
3. Tipear `:?` → debería aparecer la lista en notify (NO en el chat
   del agent).
4. Tipear `:l` → debería abrirse el status de cortex-net (slash command
   transformado).
5. Tipear `:n` → debería notify con la sugerencia actual.
6. Tipear `hola mundo` → debería ir al agent normal (no interceptar).
7. Tipear `:undefined_hotkey` → debería ir al agent normal (continue).
8. Sin cortex_sync_ticket previo, intentar invocar cortex_create_spec
   (vía agent) → debería ver el warning antes del error del MCP.
