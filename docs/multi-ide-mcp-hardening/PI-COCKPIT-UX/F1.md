# F1 — Singleton de estado + Cockpit widget read-only

Primera fase del overhaul UX. Establece la **columna vertebral** del
sistema: un singleton de estado que cualquier extensión Cortex puede
leer/escribir, y un widget persistente arriba del editor que muestra
sesión activa, rol propio, peers y agent activo en tiempo real.

> Estado: ✅ **completa**

## Lo que entrega

### 1. `_cortex-state.ts` (singleton compartido)

Módulo de estado compartido. Lo importan las extensiones Cortex que
necesitan estado común.

> ⚠ **Descubrimiento runtime (post-implementación)**: el prefijo `_`
> en el nombre NO evita que Pi lo cargue como extension. Pi escanea
> todos los `.ts` de `.pi/extensions/` y exige una factory function
> por archivo. Para que no falle con *"Extension does not export a
> valid factory function"*, este módulo exporta un `default function`
> no-op al final. El uso real sigue siendo via exports nombrados.

**API pública:**

```typescript
// Tipos exportados
export type CortexRole = "sddwork" | "designer" | "explorer" | ...;
export const CORTEX_ROLES: readonly CortexRole[];
export const AGENT_TO_ROLE: Record<string, CortexRole>;
export interface PeerSnapshot { role, pid, session_id, model, last_heartbeat, status? }
export interface TranscriptSnapshot { ts, kind, msg_id, from_role, to_role, msg_type, body, reply_to_msg_id? }
export interface Suggestion { label, hotkey, reason }
export interface CortexState {
  cwd, sessionId, sessionOpenedAt,
  activeAgentName, myRole, isMaster, myModel,
  peers, recentTraffic, suggestion,
  lastUpdate
}

// Estado singleton (lectura directa) y pub/sub
export const cortexState: CortexState;
export function subscribe(fn: () => void): () => void;
export function update(patch: Partial<CortexState>): void;
export function reset(): void;
export function resolveRoleFromAgentName(agentName?: string | null): CortexRole | null;
```

**Convenciones:**
- `sessionId === null` → standby (no hay Cortex Session activa).
- `myRole === null` → el agent activo no participa de la red
  (cortex-sync, o agent desconocido).
- `isMaster === true` → este proceso levantó el hub de cortex-net.
- Mutar estado solo vía `update(patch)`. Eso notifica a suscriptores.

### 2. `cortex-cockpit.ts` (extension nueva)

Widget persistente arriba del editor + status bar multi-key con 3 slots.

**Hooks usados:**
- `session_start` → seed inicial desde `.cortex/session.lock`, suscripción
  al singleton, registro del widget, inicio del polling.
- `before_agent_start` → actualiza `activeAgentName` + `myRole`.
- `turn_end` → re-render explícito (refresca elapsed time).
- `session_shutdown` → unsubscribe, clearInterval, reset del singleton.

**Renders:**
- **Standby** (sin sesión): mensaje breve + tip de qué hacer.
- **Sync activo** (B' anchor): "sync (B' anchor — fuera de la red)".
- **Middle**: header con session id + tiempo + MASTER/WORKER, rol propio,
  lista de peers con status (icono según idle/busy/observe), footer
  con hint del panel y hotkeys (que F2 implementa).

**Status bar (3 slots `setStatus`):**
- `cortex-session`: `⬡ <id corto> · <tiempo>`
- `cortex-role`: `<rol> · MASTER` / `<rol> · WORKER`
- `cortex-peers`: `<N> peers (<idle>i/<busy>b)`

**Polling de respaldo:** cada 3s lee `session.lock` por si la sesión
cambió fuera-de-banda (otra Pi la cerró). El polling es defensivo —
en el camino feliz, los hooks de cortex-net ya propagan los cambios
inmediatamente.

### 3. Modificaciones a `cortex-net.ts`

cortex-net pasa a ser **productor** del singleton. Cambios mínimos
y quirúrgicos (sin tocar la lógica del hub/client):

| Punto del lifecycle | Update al singleton |
|---|---|
| Import | `import { update as updateCortexState, type PeerSnapshot } from "./_cortex-state"` |
| `session_start` (después de resolver session_id) | `cwd, sessionId, myModel` |
| `session_start` (después de `tryStart` del hub) | `isMaster: hub !== null` |
| `session_start` (al final) | inicia `peerPollHandle = setInterval(5s)` que llama `client.listPeers()` y escribe `peers` |
| `ensureRegisteredAs` (éxito) | `myRole: role, isMaster: hub !== null` |
| `ensureRegisteredAs` (fallo) | `myRole: null` |
| `before_agent_start` (agent = cortex-sync) | `myRole: null` |
| `session_shutdown` | `clearInterval(peerPollHandle)`, `peers: [], myRole: null, isMaster: false` |

**Por qué polling de 5s en F1 y no eventos:** los eventos push-based
del hub (`peer_joined`, `peer_left`) son trabajo de F3. F1 establece
el contrato y la integración usando polling como solución mínima
viable. F3 reemplaza el polling sin tocar al consumidor (cockpit).

### 4. `settings.json`

`cortex-cockpit.ts` agregado a `defaultExtensions` (después de
`cortex-net.ts` para que el singleton ya esté sembrado cuando arranque).

## Contratos clave

### El singleton como bus de datos

El singleton **no es un orquestador** — es un bus de lectura. Quién
escribe qué:

| Field | Escritor canónico | Cuándo |
|---|---|---|
| `cwd` | cortex-cockpit + cortex-net | session_start |
| `sessionId` | cortex-net (primario), cortex-cockpit (polling) | session_start + polling |
| `sessionOpenedAt` | cortex-cockpit (mtime del lock) | session_start |
| `activeAgentName` | cortex-cockpit | before_agent_start |
| `myRole` | cortex-net | ensureRegisteredAs + branch cortex-sync |
| `isMaster` | cortex-net | session_start (post hub start), ensureRegisteredAs |
| `myModel` | cortex-net + cortex-cockpit | session_start |
| `peers` | cortex-net | poll cada 5s |
| `recentTraffic` | (vacío en F1) | F3 |
| `suggestion` | (vacío en F1) | F2 |

### Idempotencia

- Múltiples `update({sessionId: "x"})` con el mismo valor disparan el
  notify igual. Los suscriptores deben ser idempotentes — el `refresh`
  del cockpit re-emite `setWidget` con el mismo id, que Pi reemplaza
  in-place.
- `reset()` puede llamarse sin sesión activa sin efectos secundarios.

### Cleanup en shutdown

Tanto cortex-net como cortex-cockpit limpian su parte del singleton
en `session_shutdown`. El cockpit hace `reset()` completo; cortex-net
solo limpia `peers/myRole/isMaster` (mantiene `sessionId/cwd/myModel`
por si hubo una transición rara). Como cortex-cockpit hace `reset()`
después, el estado final queda limpio.

## Lo que F1 NO incluye (de paso)

- **Hotkeys virtuales (`:n`, `:t`, `:d`)** → F2.
- **Gates de gobernanza** (interceptar `tool_call`) → F2.
- **Sugerencia contextual rica** ("Esperando reply de X") → F2.
- **Status pings de peers** (idle/busy/observe poblado) → F3.
- **Eventos push del hub** (`peer_joined`, `peer_left`) → F3.
- **Panel modal grande `/cortex`** → F4.
- **Auto-spawn de terminales** → F5.

## Gaps abiertos (no bloqueantes)

1. **Slash commands de cortex-net que mutan `currentRegisteredRole`** (`/cortex-mode`, `/cortex-role`, `/cortex-net-shutdown`) NO propagan al singleton hoy. El próximo `before_agent_start` lo arregla, pero hay una ventana de inconsistencia. Se cubre en F3 cuando refactoreamos el lifecycle de cortex-net.
2. **El `peer.status`** en `PeerSnapshot` queda en `undefined` hasta F3 — el hub no lo emite todavía. El cockpit muestra "?" en ese caso (transparente).
3. **Validación TS** no se corrió: no hay `tsconfig.json` en este repo para extensiones del bundle (los `.ts` los compila Pi al cargarlos). Cualquier issue de tipos se detecta al arrancar Pi.

## Cómo probarlo (manual, hasta que tengamos tests)

1. `cortex setup agent --ide pi` en un proyecto adopter (regenera bundle).
2. `cd <adopter>` y `just cortex`.
3. Esperar al notify de `cortex-net` y al render del widget arriba.
4. Verificar status bar abajo con los 3 slots.
5. `/system cortex-SDDwork` → ver que el rol cambia en el widget y la status.
6. Abrir otra terminal `just role-designer` → ver que la primera muestra el peer en su lista.
7. `cortex_close_session` (vía documenter) → ver que el widget vuelve a standby.

Si algo falla: `ls ~/.cortex/logs/` para ver stderr del wrapper MCP, y
`pi` también imprime errores de carga de extensiones en su startup.
