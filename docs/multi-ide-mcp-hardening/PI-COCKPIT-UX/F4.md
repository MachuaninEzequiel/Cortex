# F4 — Panel `/cortex` on-demand (TUI modal grande)

Cuarta fase. La interfaz **principal** de control de Cortex Pi: un
panel TUI grande, navegable con flechas, que el usuario invoca con un
solo slash command (`/cortex`). Reemplaza la necesidad de recordar 4-5
comandos sueltos (`/cortex-net`, `/cortex-mode`, `/cortex-role`,
`/cortex-net-shutdown`) — esos siguen existiendo como aliases por
compat, pero la doc apunta a `/cortex` como entry point único.

> Estado: ✅ **completa**

## Lo que entrega

### `cortex-panel.ts` (nueva extension)

Una sola pieza: registra `/cortex` y abre el panel con `ctx.ui.custom()`.

#### Vistas

Dos vistas según `cortexState.isMaster`:

**MASTER** (este proceso levantó el hub):
- Mandar mensaje a un peer
- Broadcast a todos los peers
- Agregar peers al team (auto-spawn de terminales) — **F5 pendiente**
- Cambiar a documenter (preparar cierre)
- Ver transcript completo
- Audit log de la red
- Status de la red (peers + sesión)
- Cambiar modo (Full / Solo)
- Cambiar de rol propio
- Cerrar sesión sin documenter (abandonar)
- Salir de la red (este proceso)

**WORKER** (cliente de un hub externo):
- Mandar mensaje a un peer
- Broadcast a todos los peers
- Ver transcript completo
- Status de la red
- Cambiar de rol propio
- Salir de la red

Las acciones se filtran por el campo `masterOnly` del `ActionItem`. Si
master agrega o saca un peer al team, la próxima apertura del panel
muestra el set actualizado (el filtro es puro sobre `cortexState`).

#### Estructura del Component

`CortexPanelComponent` implementa el shape `{render, handleInput, invalidate}`
esperado por `ctx.ui.custom`:

- **`render(width)`**: dibuja header (sesión + rol + master/worker),
  lista de acciones con cursor `▶`, snapshot de peers con status
  coloreado (idle=success, busy=warning, observe=accent, ?=muted),
  footer con hints (`↑↓ enter esc`).
- **`handleInput(data)`**: matchea raw escape sequences:
  - `\x1b` o `"escape"` → `done(null)` (cierra).
  - `\x1b[A` o `"up"` → focus arriba.
  - `\x1b[B` o `"down"` → focus abajo.
  - `\r` / `\n` / `"enter"` → `done(action.id)` (ejecuta).
  - Otros: ignora silenciosamente.
- **`invalidate()`**: no-op (render es puro sobre `cortexState`, mutado
  externamente).

El Component no mantiene estado fuera del `focusedIdx`. La lista de
acciones se recomputa al construir (filtro master/worker se aplica una
vez al abrir).

#### Despacho de acciones

El handler de `/cortex` espera al `done(action)` del Component y
ejecuta un `switch` sobre el `action.id`. Tres patrones:

1. **Acciones complejas con sub-flow** (`send_message`, `broadcast`,
   `abandon_session`): cascada de `ctx.ui.select` y `ctx.ui.confirm`
   dentro del handler. Para `send_message`, ejemplo:
   - elegir destinatario (SelectList de peers con status)
   - elegir tipo (question/proposal/blocker/handoff)
   - emite notify con el comando tool-ready que el agent debería invocar.
2. **Acciones que mapean a slash commands existentes** (`change_mode`,
   `change_role`, `switch_documenter`, `view_audit`): emiten `notify`
   con la instrucción. Decisión: **no duplicamos lógica**. Si el panel
   ejecutara `/cortex-mode` directamente, dos implementaciones podrían
   driftear (los handlers de cortex-net.ts ya tienen su propia TUI con
   `ctx.ui.select`).
3. **Acciones pendientes** (`team_spawn` → F5): emiten `notify` warning
   con instrucción manual hasta que F5 las implemente.

#### ¿Por qué no invocar tools/slash directamente?

`pi.execTool` o `pi.runCommand` **no están documentados** en el API
público de Pi. El handler tiene tres opciones:
- Duplicar la lógica (genera drift y mantiene dos lugares para arreglar).
- Pedir al usuario que tipee el comando (pierde la UX de un solo click).
- Emitir un notify con el comando tool-ready (compromiso actual).

Optamos por la tercera. Cuando descubramos un API para invocar
programáticamente (o lo agregue una versión futura de Pi), cambiamos
los notify por ejecución real sin tocar el resto del flujo.

## Decisiones tomadas

| Decisión | Elección | Justificación |
|---|---|---|
| Vista master vs worker | **B (diferenciada)** según `isMaster` | Decisión explícita del usuario. Las acciones globales solo desde quien levantó el hub. |
| Sub-flow para mensaje | **Cascada de `ui.select`** | Más simple que componer Container con SelectList + Input simultáneos (focus routing no documentado). |
| Acciones MCP / slash | **Notify hints, no ejecución directa** | Falta API para invocar slash commands o tools programáticamente. Evita drift de lógica duplicada. |
| Ítems pendientes (F5) | **Marcador `[F5 pendiente]`** | Visible en el panel sin esconderse. Cuando F5 esté listo, basta cambiar el handler. |
| Status coloreado | Sí, tokens semánticos | Aprovecha el `peer.status` que F3 ya pobló. Cero costo extra. |
| `view_status` | Acción dedicada | Es un "info dump" rápido para usuarios que no entienden el cockpit todavía. |

## Gaps abiertos (no bloqueantes)

1. **`ctx.ui.custom` con `overlay: true`**: no probado. Si Pi lo
   soporta sin bloquear el chat por completo, podríamos hacer el panel
   no-modal en una iteración futura.
2. **Escape sequences**: los matching de `\x1b[A`/`\x1b[B` cubren xterm
   estándar. Terminales raros (algunos Windows legacy) podrían no
   funcionar. La defensa con `"up"`/`"down"` strings es un placeholder
   por si Pi normaliza eventos.
3. **Sin paginación**: si la lista de acciones crece, no scrollea (todas
   se renderizan). Para ~12 ítems alcanza, pero si llegamos a 20+
   hay que agregar viewport.
4. **No invoca slash commands programáticamente**: ver "¿Por qué no..."
   arriba. Es un trade-off explícito.

## Cómo probarlo (manual)

1. Setup adopter + `just cortex`. Esperar cockpit y autopilot.
2. Tipear `/cortex` → debería abrirse el panel modal.
3. Sin sesión, debe mostrar header "Sin Cortex Session activa" + acciones
   limitadas.
4. Navegar con flechas, ver el cursor `▶` moverse.
5. Esc → cierra sin hacer nada.
6. Reabrir y enter sobre "Status de la red" → notify con resumen.
7. Reabrir y enter sobre "Cambiar modo" → notify con instrucción `/cortex-mode`.
8. Con sesión activa + peer en otra terminal, abrir panel → enter sobre
   "Mandar mensaje" → SelectList con peer disponible → tipo → notify con
   comando.
9. Como worker (cliente del hub levantado por otra Pi), ver que las
   acciones master no aparecen.
