# F3 — Bonus cortex-net (status pings + broadcast + peer events)

Tercera fase del overhaul UX. Extiende el protocolo cortex-net con
tres aditivos que mejoran tanto el feel del multi-terminal como la
visibilidad del cockpit, sin romper consumidores existentes.

> Estado: ✅ **completa**

## Lo que entrega

Todo dentro de `cortex-pi/.pi/extensions/cortex-net.ts`. Sin archivos
nuevos. Cero cambios al backend Python.

### 1. Status por peer (idle/busy/observe)

Nuevo tipo `PeerStatus = "idle" | "busy" | "observe"`. Cada peer
mantiene su status y lo envía:

- **En `register`**: status inicial. Default `"idle"`; `documenter`
  arranca con `"observe"`.
- **En `heartbeat`** (cada 5s): status actual. Si cambió respecto al
  guardado en el hub, dispara un `peer_event`.

**Quién rota el status del lado del cliente:**

| Hook de Pi | Acción |
|---|---|
| `turn_start` | `setStatus("busy")` (excepto documenter que queda `observe`) |
| `turn_end` | `setStatus("idle")` (excepto documenter) |
| `documenter` rol | siempre `observe` — no rota |

El cockpit (F1) ya tenía el campo `status?` en `PeerSnapshot`; ahora
queda poblado y el render lo colorea: success (idle), warning (busy),
accent (observe).

### 2. Eventos push del hub (`peer_event`)

Nuevo `kind: "peer_event"` con tres `event_op`:

- `"joined"`: el hub la emite tras un `register` exitoso, a todos los
  peers de la misma sesión.
- `"left"`: el hub la emite tras un `unregister` o un `pruneStale`.
- `"status_changed"`: el hub la emite cuando un heartbeat trae un
  status distinto al guardado.

**Cliente**: nuevo callback público `onPeerEvent` que el handler de
la extensión enchufa para mutar `cortexState.peers` quirúrgicamente
(sin esperar al polling). Self-events de `joined` se filtran (el hub
broadcastea al recién registrado también, pero el client ya tiene su
propio rol y no lo necesita).

**Polling de respaldo**: el `setInterval` que sembró F1 se mantiene
pero baja de 5s a **15s**. Cubre la ventana en que el hub se reinicia
y un peer perdió eventos. En operación normal, el polling no agrega
información — los push events ya hicieron el trabajo.

### 3. Tool `cortex_net_broadcast`

Nueva tool MCP registrada vía `pi.registerTool({name: "cortex_net_broadcast", ...})`.

**Parámetros**: `msg_type` + `body`. NO acepta `to_role` — el destino
son todos los peers de la sesión actual (fanout 1:N).

**Comportamiento**:
- El hub itera todos los peers en la misma sesión (excluyendo el
  emisor) y los entrega como si fueran `send` individuales (mismo
  `msg_id` para todos).
- Cada delivery escribe una línea en el transcript con destinatario
  específico, así el documenter puede reconstruir el fanout completo.
- **No espera replies**. Si hace falta una respuesta agregada, usar
  `cortex_net_send` 1:1 al peer correspondiente.

**Restricción de tipo**: `handoff` está vetado (no podés delegar el
turno a N peers). La tool devuelve error explicativo.

**Audit**: log entry con `op: "broadcast"` + `delivered: N`.

### 4. Cleanup de polling

El comentario *"F3 va a reemplazarlo por eventos peer_joined / peer_left"*
que sembró F1 se concretó. El polling sigue como respaldo, no como
fuente primaria.

## Contratos modificados

### `Peer` (hub-side)

Antes:
```typescript
interface Peer {
  role, pid, session_id, model, last_heartbeat, socket_path;
}
```

Después:
```typescript
interface Peer {
  role, pid, session_id, model, last_heartbeat, socket_path,
  status: PeerStatus;  // ← NUEVO en F3
}
```

### `NetMessage` (wire format)

- Nuevo `kind: "broadcast" | "peer_event"`.
- Nuevo field opcional: `status?: PeerStatus` (en register + heartbeat).
- Nuevos fields para `peer_event`: `event_op?`, `event_role?`,
  `event_status?`.

### Respuesta de `list`

Antes:
```json
{ "peers": [{ "role", "session_id", "model", "pid" }] }
```

Después:
```json
{ "peers": [{ "role", "session_id", "model", "pid", "status" }] }
```

Compatible hacia atrás: clientes viejos que ignoran `status` siguen
funcionando.

### Client API

Métodos nuevos:
- `client.setStatus(status: PeerStatus): void`
- `client.getStatus(): PeerStatus`
- `client.broadcast(msgType, body): Promise<{msg_id, ok, delivered, error}>`
- `client.onPeerEvent: ((ev) => void) | null` (callback público)

Métodos existentes: sin cambios de firma.

## Decisiones tomadas

| Decisión | Elección | Justificación |
|---|---|---|
| Default status de documenter | `"observe"` | Su rol es observar in-flight. Que arranque "idle" daría falsa señal de disponibilidad para inbounds dirigidos. |
| Mantener polling de respaldo | Sí, a 15s | Robustez ante hubs que se reinician. 15s es invisible para UX. |
| Filtrar self-event `joined` | Sí, en el client | Evita doble notify en el peer recién registrado. |
| `broadcast` rejects `handoff` | Sí, error claro | Semánticamente sinsentido. El error guía al uso correcto. |
| `broadcast` no espera replies | Sí, fire-and-forget | Coherente con la intención (fanout 1:N para anuncios). |
| Status update vía heartbeat (no eager send) | Sí | El rate-limit del hub procesa mejor pulsos regulares que ráfagas. Latencia máxima = 5s (HEARTBEAT_MS). |

## Implicación en el cockpit (F1) y autopilot (F2)

- **Cockpit**: la línea de peers ahora muestra `idle`/`busy`/`observe`
  con color semántico. Cuando un peer entra/sale, el cockpit redibuja
  inmediatamente (sin esperar 5s del polling viejo).
- **Autopilot**: la regla "Sin peers — abrí terminales" no cambia; la
  regla "Coordiná con peers" gana precisión cuando hay status (la
  versión actual no la usa todavía, pero F4 va a poder decir
  "implementer está busy, esperá" sin trabajo extra).

## Gaps abiertos (no bloqueantes)

1. **Status del cliente no se propaga al hub por `setStatus` eager**:
   espera al próximo heartbeat (≤5s). Si la latencia importa, agregar
   un flush opcional. En la práctica el cockpit muestra el cambio en
   ≤5s, suficiente para UX humana.
2. **Cross-session broadcasts**: el hub filtra por session_id pero no
   logguea cross-session broadcasts bloqueados. Edge case poco común.
3. **Eventos `peer_event` no entran al audit log del hub**: van solo
   al transcript de la red. Si queremos auditoría histórica de
   entradas/salidas, agregar `logAudit` en `broadcastPeerEvent`.

## Cómo probarlo (manual)

1. `just role-sddwork` en T1 → notify "registrado como sddwork (hub)".
2. `just role-designer` en T2 → notify "registrado como designer".
3. En T1 verificar que el cockpit muestra designer con status idle.
4. En T2 mandá un mensaje desde el agent → T1 ve a designer pasar a busy
   durante el turno y volver a idle al finalizar.
5. `just role-documenter` en T3 → T1 y T2 ven al documenter con observe.
6. En T1 (sddwork) invocar `cortex_net_broadcast(question, "test")` →
   T2 y T3 reciben el inbound; T1 ve `delivered: 2` en la respuesta.
7. Cerrar T2 → T1 y T3 ven a designer desaparecer del cockpit al toque.
